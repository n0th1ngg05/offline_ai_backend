# Auth Backend

FastAPI auth service: Super Admin login with email OTP (Gmail SMTP),
forgot/reset password, JWT issuance. Built to match an already-existing
frontend's fixed API contract exactly (see `AUTH_BUILD_SPEC.md` for the
full contract trace).

Stack: Python 3.10 · FastAPI · PostgreSQL 16 · SQLAlchemy 2.0 (asyncpg) ·
Redis 7. Bare metal only in this phase — no Docker.

## 1. Prerequisites

- Python 3.10 (use `py -3.10` on Windows if multiple versions are installed)
- PostgreSQL 16, running locally, with `psql`/`createdb` on PATH
- Redis 7, running locally

## 2. Database setup

```bash
createdb auth_backend
psql -d auth_backend -f sql/init.sql
```

This creates the `offlineai` schema, the `users` table, and seeds one
Super Admin:

```
email:    humza.ahmad050504@gmail.com
password: n0th1ng#8240
```

Verify:
```bash
psql -d auth_backend -c "\dn"      # should list schema 'offlineai'
psql -d auth_backend -c "SELECT email, user_type, status FROM offlineai.users;"
```

## 3. Python environment

```bash
python3.10 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\Activate.ps1

pip install --upgrade pip
pip install -r requirements.txt
```

## 4. Environment file

```bash
cp .env.example .env
```

Edit `.env`:
- Set `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB=auth_backend`
  to match your local Postgres setup.
- Set `JWT_SECRET_KEY` to a real random string:
  ```bash
  python -c "import secrets; print(secrets.token_hex(32))"
  ```
- Leave `SMTP_DEV_MODE=true` for now — OTP codes will print to the console
  instead of being emailed, so you can test the whole flow before setting
  up Gmail SMTP. See section 6 below for enabling real email sending.

## 5. Run it

```bash
uvicorn app.main:app --reload --port 8000
```

You should see:
```
[Startup] Verifying Redis connection...
[Startup] SMTP_DEV_MODE is ON — OTP/reset emails will be printed to the console...
```

Confirm:
```bash
curl http://localhost:8000/health
```

Interactive API docs (auto-generated by FastAPI): `http://localhost:8000/docs`

## 6. Enabling real Gmail SMTP (when ready)

1. Enable 2-Step Verification on the Gmail account:
   `myaccount.google.com/security`
2. Generate an App Password: `myaccount.google.com/apppasswords`
   (requires 2FA to already be on — the option won't appear otherwise)
3. Copy the 16-character password it gives you
4. In `.env`:
   ```
   SMTP_USERNAME=your_account@gmail.com
   SMTP_PASSWORD=<16-char app password, no spaces needed either way>
   SMTP_FROM_EMAIL=your_account@gmail.com
   SMTP_DEV_MODE=false
   ```
5. Restart the server. OTP emails will now actually send via
   `smtp.gmail.com:587`.

## 7. Testing the full flow with curl

### Step 1 — Login (triggers OTP)

```bash
curl -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"identifier":"humza.ahmad050504@gmail.com","password":"n0th1ng#8240"}'
```

Expected: `{"success": true, "message": "OTP sent to your email.", "verification_required": true, ...}`

With `SMTP_DEV_MODE=true`, check the **server's terminal output** — the
6-digit code will be printed there, inside a `[DEV MODE] EMAIL NOT
ACTUALLY SENT` block.

### Step 2 — Verify OTP (issues JWT)

```bash
curl -X POST http://localhost:8000/api/v1/auth/verify \
  -H "Content-Type: application/json" \
  -d '{"identifier":"humza.ahmad050504@gmail.com","otp":"<code from server console>"}'
```

Expected: `{"success": true, "message": "Login successful.", "data": {"access_token": "...", "user_type": "super_admin", ...}}`

### Step 3 — Call a protected route

```bash
TOKEN="<access_token from step 2>"
curl http://localhost:8000/api/v1/auth/me -H "Authorization: Bearer $TOKEN"
```

### Forgot password flow

```bash
# 1. Request a reset code
curl -X POST http://localhost:8000/api/v1/auth/forgot-password \
  -H "Content-Type: application/json" \
  -d '{"email":"humza.ahmad050504@gmail.com"}'
# check server console for the code (dev mode)

# 2. Verify it, get a reset_token
curl -X POST http://localhost:8000/api/v1/auth/forgot-password/verify \
  -H "Content-Type: application/json" \
  -d '{"email":"humza.ahmad050504@gmail.com","otp":"<code>"}'

# 3. Reset the password using the reset_token from step 2
curl -X POST http://localhost:8000/api/v1/auth/reset-password \
  -H "Content-Type: application/json" \
  -d '{"reset_token":"<reset_token from step 2>","new_password":"a_new_strong_password_1"}'
```

After this, log in again with the NEW password to confirm it took effect.

## 8. Connecting the real frontend

In the frontend's own `.env` (or `.env.local`):
```
VITE_API_BASE_URL=http://localhost:8000
```

The frontend's `AuthPage.jsx` → `UserLoginAction` → `/api/v1/auth/login`
→ OTP step → `UserVerificationAction` → `/api/v1/auth/verify` flow should
now work end-to-end against this backend with zero frontend code changes,
since every endpoint and response shape here was built to match its
existing, fixed expectations exactly.

## 9. File structure

See `AUTH_BUILD_SPEC.md` section 7.5 for the full rationale. Summary:

```
app/
├── core/       config, database, redis, security (hashing/JWT only), response envelope
├── models/     user.py — the offlineai.users ORM model
├── schemas/    auth.py — Pydantic request models
├── services/   otp_service, mailer_service, auth_service, user_service — one concern per file
└── api/v1/     auth.py — thin router, no business logic
```

When adding new logic: HTTP shape → router; business rule → a `*_service.py`;
raw DB query → `user_service.py` (or a new `*_service.py` per entity later);
OTP logic → `otp_service.py` only; email sending → `mailer_service.py` only.

## 10. Known limitations of this phase (by design, not oversight)

- No refresh tokens — a 24h access token expires to a plain re-login.
- No logout/token revocation — a leaked token is valid until it expires.
- `/auth/register`, `/auth/activate`, and the student-login endpoints the
  frontend also calls are NOT implemented yet — out of scope for this
  phase (Super Admin login/OTP/reset only, per the user's explicit scope).
- Super Admin creating schools/users/admins is the next phase, not this one.
- Bare metal only — Docker packaging is a later phase.
